# Aruba Mini Dashboard 성능 검증 보고서

## 측정 원칙

성능 수치는 동일한 명령과 임계값을 사용하는 비식별 fixture 실행 또는 패키지
실행에서만 비교합니다. 실제 Aruba 장비, 느린 사내망, 저사양 노트북에서 측정하지
않은 값은 추정해서 기재하지 않습니다.

기준 소스는 `01df236a1689457f0119ba463264aa5ecdc66d44`입니다. 측정 PC는

## v0.3.0 변경 후 결과

같은 개발 PC에서 v0.3.0 소스를 다시 측정했습니다. 초기 화면 측정은 첫 설정
안내가 측정값을 가리지 않도록 기본 설정 파일을 미리 둔 뒤 5회 수행했습니다.
Windows 캐시를 제거한 cold boot, 저사양 PC와 HDD 측정은 아닙니다.

v0.3.1에서는 현재 등록·관측 장비와 활성/확인 대기 상태를 보호하면서 오래된
미등록 장비 snapshot도 180일·10,000개로 제한했습니다. 이 patch의 목적은 MM의
장비 목록이 장기간 크게 바뀌는 환경에서 시작 메모리와 SQLite 행 수가 계속
증가하지 않게 하는 것이며, 아래 v0.3.0 측정값을 새 수치로 바꾸어 주장하지 않습니다.

추가 offscreen 회귀에서 500개 전체 보기 행에 같은 snapshot을 다시 표시하는 데
감사 시점 구현은 약 22.0초가 걸렸습니다. 행 signature 캐시 적용 후 같은 개발
환경의 연속 3회는 0.028~0.030초였으며, 변경된 행만 아이콘·글꼴·tooltip을 다시
설정합니다. 이는 실제 Intel 내장 그래픽이나 100/125/150% 배율 측정이 아닙니다.

| 항목 | v0.3.0 결과 |
|---|---|
| 소스 초기 화면 표시 5회 평균 | 552.1ms (기준 1,029.8ms 대비 46.4% 감소) |

| Qt 번역 파일 | 2개 / 156,883바이트 |
| ZIP 크기 | GitHub 릴리스 자산 생성 후 릴리스 본문에 기록 |

1,024회 반복 처리의 평균은 기준보다 14.3%, P95는 13.7% 낮았습니다. 측정 중
Working Set 증가는 기준의 20.551MiB에서 3.988MiB로, Private Bytes 증가는
19.789MiB에서 4.137MiB로 줄었습니다. 기존 측정 절차 설명을 바탕으로 재구성한
비식별 fixture 스트레스 결과이므로 24시간 메모리 누수 검증을 대신하지 않습니다.

추가 마이크로벤치에서 12개의 작은 저장을 각각 transaction으로 실행한 경우는
평균 0.7803ms, 한 transaction으로 묶은 경우는 0.5727ms였습니다. 4,096바이트
SSH chunk 1,000개 누적은 전체 재검사 방식 2,405.65ms에서 제한 누적기 7.43ms로
줄었습니다. 모두 NVMe와 합성 데이터의 hot-cache 결과이므로 HDD·실제 장비의
절감률로 일반화하지 않습니다.

저사양 모드의 반복성이 높은 4MiB 출력 3개는 12,582,912바이트에서 79,527바이트로
압축되었고 생성 평균은 27.270ms, 4MiB 한 항목의 지연 해제 평균은 5.528ms였습니다.
압축되지 않는 출력은 원문으로 보관하므로 이 비율 역시 실제 Aruba 출력의 예상값이
아닙니다.

### 소스에 적용한 최적화 계약

- 장비 점검은 GUI 메인 스레드 밖에서 실행하고 앱 전용 Qt worker 풀의 동시
  실행 수를 1개로 제한합니다. 점검 중 반복 실행은 기존 중복 방지 정책을
  유지합니다.
- 일반 모드는 MM과 클러스터를 최대 2개 작업으로 수집합니다. 저사양 모드는
  두 수집을 순차 실행하고 자동 점검 간격을 설정값과 120초 중 큰 값으로
  적용합니다. 수동 `지금 점검`은 즉시 실행됩니다.
- 저사양 모드 여부와 관계없이 실행 명령, 출력 한도, 파서, 감지 임계값,
  연속 감지·복구 및 IP 종합 결과는 바뀌지 않습니다.
- SSH 출력은 매 chunk마다 전체 문자열을 다시 만드는 대신 제한된 누적기로
  처리하며, 출력 한도·pager 처리·취소·timeout과 유한 재시도 backoff를
  유지합니다.
- 점검 결과, detector 상태, 최근 정상 상태와 Failover 저장을 묶어 SQLite
  transaction과 작은 디스크 쓰기 횟수를 줄입니다. 저장 실패는 원자적으로
  rollback하고 다음 저장에서 다시 시도합니다.
- 종료 장애, 일반 사건, 확인 완료 Connection-Type 변화와 Failover 이력은 하루 최대 한 번 정리하며 각 테이블의
  보관 범위를 최근 180일·최대 10,000건으로 제한합니다. 활성 장애와 확인 대기
  상태는 보호하며 자동 `VACUUM`은 실행하지 않습니다.
- 현재 보이는 표만 갱신하고 숨은 표는 최신 snapshot만 보관했다가 표시 시
  렌더링합니다. 상세 창과 원본 표시는 요청할 때 생성하고, 아이콘을 재사용하며,
  UI 설정의 SQLite mirror 쓰기는 debounce 후 묶어서 처리합니다.
- 운영 로그는 회전 한도를 유지하고, 저사양 모드에서는 일반/SSH 디버그 로그를
  2MB·백업 2개로 축소합니다. 선택적 성능 로그는 기본 꺼짐이며 1MB·백업 2개로
  제한합니다.
- Windows 패키지는 onefile 압축 해제를 피하는 onedir 방식을 유지합니다.
  한국어 Qt 번역만 포함하고 실행에 불필요한 CLI 보조 모듈을 제외하되,
  Netmiko 장비 드라이버와 Paramiko 등 SSH 실행 경로는 유지합니다.

소스 측정과 별도로 v0.3.0 최종 onedir의 smoke·크기·인벤토리를 재검증하고,
목표 저사양 PC와 느린 네트워크에서는 현장 검수해야 합니다.

## 자동화 검증 항목

- 일반 모드와 저사양 모드의 세 명령, 파싱 결과, 문제 IP와 사건 일치
- 점검당 SQLite transaction 상한과 저장 실패 원자 rollback
- 활성 사건·pending 변화 보존 및 종료 이력 한도
- SSH 작은 chunk, CR/LF 경계, 출력 제한, pager, 취소와 재시도 backoff
- 숨은 표 렌더링 보류, 상세 원본 지연 로딩, 설정 저장 debounce
- 반복 fixture 실행의 CPU, 메모리, 스레드, 핸들, DB와 로그 증가량
- PyInstaller onedir, 압축 해제 EXE smoke와 패키지 인벤토리
- 실제 대시보드·fixture worker 한 회 실행 후 thread pool 정상 종료 lifecycle smoke

자동 테스트 결과와 최종 패키지 값은 릴리스 시점의 검증 기록과 함께 판단하며,
이 문서만으로 실제 장비 또는 저사양 PC 통과를 주장하지 않습니다.

## 자동화로 확인하지 못하는 범위

- 저전력 듀얼코어 또는 4~8GB RAM 노트북의 실제 성능
- SATA HDD의 진정한 cold boot와 Windows 캐시 제거 후 시작 시간
- 실제 Aruba SSH 지연, 장비별 출력 크기, Failover와 네트워크 요청 시간
- 종료 요청은 자체 read loop와 재시도 대기에서 즉시 확인하지만, OS/SSH 라이브러리의
  단일 blocking 연결 호출 중에는 설정된 connect timeout까지 반환이 지연되는지 여부
- 실제 100%, 125%, 150% 배율의 GPU 렌더링 부하
- 24시간 이상 장기 운전과 조직의 알림·EDR·백신 정책
- MM에서 미등록 IP churn이 큰 환경에서 180일·10,000개 보관 정책의 실제 시작
  메모리·SQLite 크기 효과

현장 배포 전 `WINDOWS11_QA_CHECKLIST_KO.md`에 따라 별도로 검수해야 합니다.
