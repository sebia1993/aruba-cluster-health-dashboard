# 장애 판단 로직

이 문서는 Aruba MM / WLC 상태 모니터링이 어떤 관측값을 장애 증거로 사용하고, 어떤 상황에서는 판단을 보류하는지 설명합니다.

## 1. 기본 원칙

가장 중요한 원칙은 다음과 같습니다.

> **수집 실패를 장비 Down으로 바꾸지 않습니다.**

SSH 연결 실패, 명령 Timeout, 빈 출력, Parser 실패는 실제 장비 장애일 수도 있지만 네트워크 경로·계정·프롬프트·출력 변형 문제일 수도 있습니다. 따라서 해당 상황은 `확인 불가` 또는 부분 수집으로 분리합니다.

반대로 정상적으로 수집한 `show switches`가 특정 Controller를 명시적으로 `Down`으로 보고하면 해당 값은 실제 상태 증거로 사용합니다.

## 2. 상태 신호

### MM Controller 상태

명령:

```text
show switches
```

정상적으로 파싱한 결과에서 Controller가 `Down`이면 즉시 장애 신호로 반영합니다.

다만 `show switches` 명령 자체를 수집하지 못한 경우에는 Down을 추정하지 않습니다.

### Client 분배 상태

명령:

```text
show lc-cluster load distribution client
```

Active Client 수가 낮다고 한 번만 관측해서 이상으로 확정하지 않습니다.

기본값:

| 조건 | 값 |
|---|---:|
| 절대 낮은 Client 기준 | 10 |
| Peer 대비 비율 기준 | 25% |
| 이상 확정 | 3회 연속 |
| 복구 확정 | 2회 연속 |
| Cluster 전체 Active 최소값 | 50 |
| Peer 중앙값 최소값 | 30 |

절대값과 Peer 상대값을 함께 보고, Cluster 전체 사용량이 충분히 낮은 상황은 `낮은 전체 사용량`으로 분리합니다.

따라서 다음 두 상황은 같은 의미가 아닙니다.

```text
WLC-A Active 5 / Peer 120 / Cluster 전체 사용량 충분
→ 특정 WLC 분배 이상 가능성

WLC-A Active 5 / Peer 8 / Cluster 전체 사용량 매우 낮음
→ 야간·저사용량 가능성, 장애로 확대하지 않음
```

### Cluster 구성원 누락

한 번의 출력에서 구성원 행이 보이지 않는다고 즉시 장애로 확정하지 않습니다.

기본 3회 연속 누락을 확인해 일시적인 출력 변동이나 부분 수집 가능성을 완화합니다.

### Connection-Type 변화

명령:

```text
show lc-cluster group-membership
```

표의 `Connection-Type` 열만 첫 정상 baseline으로 사용하고 이후 값이 달라지면
변화 사건을 생성합니다. 다음 `STATUS` 열의 `CONNECTED`, `last HBT_RSP`, `RTD`는
실시간 상태 정보이므로 Connection-Type 비교에 포함하지 않습니다.

```text
기존: L2-Connected
현재: L3-Connected
→ Connection-Type 변화 사건
```

운영자가 변화를 확인하면 반복 알림 대상에서는 제외할 수 있지만, 확인 자체가 원래 baseline으로 자동 복귀시키는 것은 아닙니다.

v0.4.2로 처음 실행할 때 이전 버전이 STATUS까지 붙여 저장한 값은 로컬 SQLite
v5 마이그레이션에서 분리합니다. 분리 후 이전값과 현재값이 같은 오탐만 자동으로
종료하고 실제 타입 변화와 과거 사건 이력은 유지합니다.

## 3. 상태 전이

Client 분배 이상은 기본적으로 다음 흐름을 따릅니다.

```text
정상
 ↓
이상 1회 → 관찰
 ↓
이상 2회 → 관찰
 ↓
이상 3회 → 이상 확정
 ↓
정상 1회 → 복구 확인 중
 ↓
정상 2회 → 복구
```

순간적인 변동과 실제 지속 이상을 분리하기 위해 streak를 사용합니다.

MM의 명시적 Controller Down은 이 streak를 기다리지 않고 즉시 반영합니다. 두 신호의 성격이 다르기 때문입니다.

## 4. 복수 원인 상관분석

여러 명령이 같은 IP에 대해 서로 다른 문제를 보고할 수 있습니다.

예:

```text
192.0.2.11
├─ show switches: Up
├─ load distribution: Active Client 연속 이상
└─ group-membership: Connection-Type 변화
```

프로그램은 이를 별도 장비처럼 분리하지 않고 같은 IP의 원인 목록으로 병합합니다.

화면에서는 다음 정보를 함께 보여줍니다.

- 종합 상태
- 문제 IP
- 주요 판단 근거
- 장비별 세부 상태

## 5. 수집 실패와 장애의 분리

| 관측 | 의미 | 최종 처리 |
|---|---|---|
| SSH 접속 실패 | 관리 경로/인증/장비 문제 가능 | 확인 불가 |
| 명령 Timeout | 응답 지연 또는 세션 문제 가능 | 확인 불가/부분 수집 |
| 빈 출력 | 명령/권한/출력 문제 가능 | 확인 불가 |
| Parser 실패 | 출력 형식 미지원 가능 | 확인 불가 |
| 정상 파싱된 MM Status Down | 장비 상태 증거 | 장애 |
| Client 이상 1~2회 | 순간 변동 가능 | 관찰 |
| Client 이상 3회 | 지속 이상 | 주의/이상 |
| Connection-Type baseline 변화 | 구성/상태 변화 | 확인 대상 사건 |

## 6. Primary/Fallback과 판단

Cluster Primary에 접속하지 못하면 Fallback Controller로 조회를 시도할 수 있습니다.

이때 두 사실을 분리합니다.

1. **Primary에서 수집하지 못했다는 사실**
2. **Fallback을 통해 관측한 Cluster 상태**

Fallback 수집 성공을 Primary 정상으로 해석하거나, Primary 접속 실패를 Cluster 전체 장애로 확대하지 않습니다.

## 7. Incident 확인과 복구

운영자의 `알림 확인`은 상태를 정상으로 바꾸는 버튼이 아닙니다.

확인은 다음 목적입니다.

- 운영자가 사건을 확인했다는 상태 기록
- 선택적으로 반복 알림 중단

실제 복구는 수집된 상태가 복구 조건을 충족했을 때 별도로 기록합니다.

```text
장애 활성
  ├─ 운영자 확인 → 장애 유지, 반복 알림 제어
  └─ 복구 조건 충족 → 복구 사건
```

## 8. 판단하지 않는 영역

이 도구는 다음을 단독으로 확정하지 않습니다.

- 무선 사용자 체감 품질의 최종 원인
- AP/RF 문제
- ClearPass/RADIUS 인증 장애
- 상위 회선 또는 방화벽 문제
- WLC 설정 오류의 구체적인 설정 줄

대시보드는 MM/WLC 상태를 빠르게 좁히기 위한 운영 보조 도구이며, 장애 조치는 추가 CLI·로그·서비스 상태와 함께 판단해야 합니다.
